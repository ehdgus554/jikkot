# 직꼿 확정 UIUX 적용·업로드·기존 운영 환경 배포 요청

현재 직꼿 프로젝트에 첨부한 확정 UIUX를 실제 코드로 구현하고, 로고·브랜드 색·폰트·인체와 루틴 이미지를 포함해 기존 운영 환경에 배포까지 완료해줘. 계획만 작성하거나 화면 캡처만 만들고 끝내지 말고 실제 코드를 수정해줘.

이 요청은 저장소 확인, 자산 업로드, 프론트엔드 구현, 기존 Firebase/API 연결, 관련 검증, 필요한 커밋·푸시, 기존 배포 경로로 운영 반영까지 승인한 요청이다. 이미 확정한 디자인이나 배포 여부를 다시 묻지 말고 진행해줘. 실제 권한·비밀키·서비스 운영 정보가 없어서 막힌 부분만 구체적으로 알려줘. 그 전에 가능한 구현·검증·배포용 빌드는 끝내줘. 실행하지 못한 배포나 인증을 성공했다고 표시하지 마.

## 1. 자료를 먼저 열고 작업 대상 확인

첨부 `jikkot-uiux-handoff-2026-10-13.zip`을 풀어 확인한다.

- `index.html`: 홈부터 모든 화면/상태를 고를 수 있는 통합 검토본. 28개 화면/상태, 검토 도구에서 회원/비회원 변경 가능. 이것 자체를 운영 앱으로 배포하면 안 된다.
- `screens/01-home.html`~`15-alternative.html`: 사용자와 정리한 주요 화면 최종본. 기존 홈·자세·부위와 이번 대화를 합친 실제 소스.
- `screens/state-*.html`: 통합본의 화면 상태별 markup 스냅샷. 원본 CSS는 index.html과 대응하며 필요한 공통 스타일을 찾아서 적용한다.
- `assets/brand`: 최종 워드마크 원본과 표시용 이미지, 홈 거북이, 마지막 부드러운 스케치 인체, 공식 Google 로고.
- `assets/fonts`: LINE Seed KR과 Nunito 실제 파일 및 라이선스.
- `assets/routines`: 승인된 동작 11개의 원본 PNG.
- `docs/screen-audit.md`: 전체 대조표, 사용자 확정 사항, 빈 상태 처리와 현재 발견사항.
- `reference/five-areas-spec.json`, `reference/routines.json`, 기존 5부위 배포 요청문: 안정적인 ID/문구/원본 동작 참고. 최신 저장소의 동일 데이터와 비교한다.

먼저 AGENTS.md, 현재 Git 상태/remote/브랜치, 프레임워크, 실제 진입 화면·라우팅, 추천/다음추천/피드백 API, Firebase 연결, 환경변수·배포 스크립트·도메인을 확인한다. 기존 작업과 사용자 데이터를 보존하고 unrelated 변경을 덮어쓰지 않는다.

대상 저장소는 `https://github.com/ehdgus554/jikkot`이다. `jikkot-ver9`는 기존 소스 이름이며 별도 배포 대상이라고 간주하지 않는다. 과거 “Firebase + Cloudflare Pages”라는 계획보다 실행 시점 저장소의 실제 구성이 우선이다. 2026-10-13에 읽은 체크아웃은 vinext 빌드 + Cloudflare Workers, `wrangler.jsonc`의 Worker 이름 `jikkot`이었다. 실제 프로젝트/계정/운영 도메인과 일치하는지 확인하고 기존 경로를 재사용한다. 새 도메인·새 Firebase 프로젝트·새 별도 사이트를 만들지 않는다.

## 2. 자료 간 우선순위

1. 이 프롬프트에 적은 사용자 최종 수정 사항.
2. `docs/screen-audit.md`와 각 화면 최종본.
3. 현재 저장소의 기존 승인된 콘텐츠 ID·추천 분기·원본 동작 데이터.
4. 통합본과 화면의 시안용 예시 데이터.

UI 개선을 이유로 추천 알고리즘·동작 목록·회원 정책을 새로 발명하지 않는다. 기존 SPEC는 반드시 5부위 버전이어야 한다. 11개의 세부 부위를 선택하게 하던 오래된 명세는 사용하지 않는다. 디자인 시안의 단축 문구나 테스트용 연결을 제품 데이터로 덮어쓰지 않는다.

첨부 안의 검토용 화면 선택기, 회원 체크박스, 미리보기 코드 123456, 메모리 회원/기록, ‘다음 화면: …’, 로그인/인증 스텁은 개발 참고용이다. 운영 코드에 남기지 않는다. 고정 ‘등’, ‘오늘 10월 13일’, 7→8 예시를 실제 사용자 데이터처럼 표시하지 않는다.

## 3. 브랜드와 공통 UI

- 메인 라이브 코랄 `#EF7564`, 서브 딥 인디고 `#252A76`를 디자인 토큰으로 관리한다. 밝은 표면, 조용한 회색 보조 글자, 얇은 경계, 둥근 카드, 여백 중심의 기존 인상을 유지한다.
- 코랄 CTA에는 딥 인디고 글자를 사용해 읽기 쉬운 대비를 확보한다. 작고 연한 글자도 실제 배경 대비를 확인한다. 임의로 브랜드 색상을 다른 색상으로 바꾸지 않는다.
- 최종 로고는 `assets/brand/wordmark-original.png`와 이를 그대로 표시한 `wordmark-ui.png`다. 텍스트 jikkot.이나 초기 로고로 대체하지 않는다. 로고 아래 ‘직꼿’ 글자를 덧붙이지 않는다. 비율과 색을 유지한다.
- 홈 캐릭터는 첨부 `turtle-home.png`의 기존 시안을 사용한다. 새로운 캐릭터를 생성하지 않는다.
- 한글 LINE Seed KR, 영문·숫자 Nunito. 첨부 실제 파일로 self-host한다. weight별 실제 파일을 선언하고 CSS/preload/MIME/CORS/캐시를 확인한다. 폰트 로딩 실패를 임의 대체 글꼴로 숨기지 않는다. 라이선스도 저장소에 포함한다.
- 로고·인체·폰트·11개 원본 PNG를 저장소의 public 정적 자산에 넣는다. 시안의 base64 이미지를 화면마다 복제하지 말고 정적 파일 경로로 바꾼다. 생성 이력과 원본 파일은 유지한다.
- Google 버튼은 **“Google로 계속하기”**로 표기하고 실제 공식 컬러 G 로고를 비율 유지해 표시한다. 로고를 손그림/단색 텍스트로 대체하거나 브랜드 코랄로 칠하지 않는다. 필요한 최종 버튼 규격은 공식 Google 가이드로 확인한다.
- 선택 카드의 장식 픽토그램은 제거한다. 이전·다음·선택 체크 같은 기능 표시와 Google 실제 로고는 유지할 수 있다.
- Header, Logo, Surface, ChoiceCard, PrimaryButton, ConsentRow, RoutineMedia, ResultSummary 등을 공통 컴포넌트로 구현한다. 화면별 마크업을 붙여 넣는 방식으로 스타일이 갈라지지 않게 한다.
- 320px~데스크톱에서 줄바꿈·패딩·2열 카드가 넘치지 않게 한다. 모바일 입력은 16px 이상, 탭 타깃은 약 44px 이상이다. 태블릿/데스크톱은 시안의 중앙 화면 밀도와 여백을 유지한다.
- 키보드 초점·스크린리더 레이블·중복 전송 방지·reduced motion을 지원한다. 테스트/검토 UI를 제품 흐름에 끼워 넣지 않는다.

## 4. 이전 채팅에서 확정한 처음 세 화면

### 홈

`01-home.html`의 구성과 문구를 사용한다. “잠깐, 몸도 쉬어갈까요?”, 기존 캐릭터, “내 몸 풀어주기”, 홈/내 기록/스트레칭/쇼핑 메뉴를 유지한다. 비회원은 로그인/회원가입과 하루 1회 안내, 회원은 기존 로그인 상태와 로그아웃을 연결한다. 스트레칭·쇼핑은 메뉴만 남기고 준비 중 안내를 띄운다.

### 자세 선택

`02-posture.html`을 사용한다. 이 채팅에서 중복 만들었다가 제외한 자세 화면을 다시 적용하지 않는다.

- 질문: “지금 어떤 상태인가요?”
- 안내: “지금 바로 할 수 있는 자세를 골라주세요. 그 자세에 맞는 동작을 찾아드릴게요.”
- 앉기: “의자에 앉아있어요.”
- 서기: “가볍게 일어설 수 있어요.”
- 눕기: “바닥에 누울 수도 있어요.”
- 단일 선택→다음→부위 선택. 자세 선택을 같은 루틴 중 반복해서 물어보지 않는다.

읽은 동작 11개의 positions는 모두 앉기였다. 실행 시 최신 승인된 콘텐츠를 확인한다. 선택 자세가 실제 동작을 지원하지 않으면 `postureUnavailable` 상태를 표시하고 앉아서 이용하기/홈을 제공한다. 서기·눕기를 선택했는데 말없이 앉기 동작을 내보내거나 승인 없는 자세 변형을 만들지 않는다. 현재 서비스의 자세 선택 의미가 ‘가능한 자세 집합’으로 이미 명시되어 있다면 그 계약을 확인해 유지하고 문구와 함께 일관되게 처리한다.

### 부위 선택

`03-body.html`의 **최종 compact soft sketch**를 사용한다. 초기 SVG 윤곽/근육이 세밀한 3D 버전으로 되돌리지 않는다.

- 머리·목·어깨·등·허리 5개 중 1개만 선택.
- 자연스러운 비율의 스케치, 절제된 입체감. 현재 이미지와 선택 영역 좌표를 비례 확대/축소한다.
- 약 16% 작게 줄인 최종 모형 크기를 유지한다.
- 마우스 호버·모바일 탭 시 해당 부위가 살짝 빛나고 부위 이름 표시. 선택 유지·해제·pointercancel·키보드 초점 처리.
- 부위 이름은 호버/선택/키보드 초점 시에만 나타난다. ‘뒷모습’ 표시 없음.
- 상세 부위 재질문/하위 메뉴 없음.

## 5. 습관부터 완료까지

- 습관·최근 행동 화면의 ‘선택한 부위’는 텍스트 표시만 한다. dropdown/select나 탭으로 변경할 수 없어야 한다.
- ‘이전’으로 부위 선택까지 돌아갈 수 있다. 부위 변경 시 이후 습관·행동·결과를 초기화하고, 습관 변경 시 이후 행동·결과를 초기화한다. 같은 답변으로 뒤로 가기를 하는 동안은 불필요하게 입력을 지우지 않는다.
- 평소 습관: “평소 어떤 습관이 있나요?” / “자주 하는 행동을 모두 골라주세요.” 복수 선택. 장식 아이콘 없는 카드.
- 최근 행동: “최근에는 무엇을 했나요?” / “오늘이나 불편해지기 직전에 한 행동을 모두 골라주세요.” 복수 선택. 마지막 버튼 “내 루틴 보기”.
- 실제 일반 항목은 기존 fiveAreasSpec의 프로필과 stable ID를 사용한다. H_UNKNOWN은 일반 습관과 배타적. R_NONE/R_UNKNOWN은 서로 및 일반 행동과 배타적. 클릭 순서가 결과를 바꾸지 않는다.
- 추천을 위해 묻는 질문은 부위·습관·최근 행동 3개뿐이다. 추가 세부 문진/후보 선택/동점 질문을 넣지 않는다. 공통 3칸 진행표시는 이 세 질문에 맞춘다.
- 세 번째 답변 제출→기존 추천 호출→선택한 사실에 근거한 짧은 이유와 공식 동작 1개. 분석은 같은 화면의 짧은 설명에 포함하거나 요청 중 상태로 처리한다. 중간 ‘결과 보기’ 단계를 새로 늘리지 않는다.
- `06-routine.html`처럼 안내 PNG 전체가 보이고 원본 확대가 가능해야 한다. 그림은 정적 PNG다. GIF·영상·추가 마사지/스트레칭 묶음을 생성하지 않는다.
- 추천 화면에는 **“동작 시작하기” 버튼이 없다. “마쳤어요” 하나만 있다.** 임의 타이머·시간 기록을 만들지 않는다.
- 피드백 질문 “동작 후 어떠세요?”: 편해졌어요 / 비슷해요 / 더 불편해요. 하나를 누르면 전송하고 다음 분기로 바로 이동. 별도 제출/다음 버튼 없음. 처리 중 버튼을 잠가 중복을 막는다.
- 편해짐: 완료 요약, 첫 화면, 회원 기록, 회원 다른 루틴. 회원은 피드백 전송 성공 후 자동 저장. 비회원에게 ‘계정 기록 저장 완료’라고 하지 않는다.
- 비슷함: 입력을 다시 묻지 않고 유효 대체 동작 1개. 이미 제시한 동작 제외. 없으면 대체 동작 없음→종료. 비회원 추가 추천 권한은 기존 하루 제한/회원 요구 계약을 유지한다.
- 불편해짐: 제목 **“어느 과정에서 불편했나요?”**와 방금 한 동작, 동작별 과정 선택, 확인/여기서 마칠게요. **“지금은 동작을 멈춰주세요”, “더 불편해진 동작을 계속할 필요는 없어요” 문장을 다시 넣지 않는다.** 추가 불편 확인은 추천 전 세 질문의 네 번째 문진이 아니라 피드백 후 단계다.
- 종료는 “조금 더 편해졌네요”처럼 개선을 단정하지 않는다. “오늘의 루틴을 마쳤어요”와 실제 피드백을 표시한다.

대체 규칙은 제품 콘텐츠다. 읽은 `nextRecommendation`은 pattern/changes를 실제 사용하지 않고 넓은 부위 후보로 넘어갈 수 있었다. 현재 코드도 같다면 승인된 대체 데이터/설정과 기존 분기 계약을 확인한다. 단순 번호순/랜덤/인기순/몸 부위 전체 순환/생성형 AI 추정으로 대체하지 않는다. 통합본의 7→8은 화면 예시이며 승인된 대체 매핑이 아니다. 적절한 대체 매핑이 없을 때는 새 규칙을 발명하지 말고 ‘추가로 안내할 동작이 없어요’ 상태로 마무리하고 확인할 콘텐츠 항목을 최종 보고에 남긴다.

## 6. 기록·회원·비회원·복원

- 회원 기록은 조회만 제공한다. 날짜·자세·부위·습관·최근 행동·추천 동작·피드백을 부위별로 묶고 펼침 상세로 표시한다. 기존 history snapshot과 ID를 유지한다. 과거 데이터를 새 이름에 맞춘다고 삭제/대체하지 않는다.
- 로그인 후 이용한 기록만 계정에 저장한다. 비회원 기록을 가입/로그인 후 가져오지 않는다.
- 로그아웃하면 비회원이다. 서버의 기존 회원 기록은 유지한다. 이전 회원의 기록·진행 상태가 비회원이나 다른 회원 화면에 보이지 않도록 owner별 복원과 화면 초기화를 한다.
- 회원은 현 단계 횟수 제한 없음. 비회원은 한국시간 기준 하루 1회. 입력 도중이 아닌 추천이 성공적으로 표시되는 시점에 기존 정책대로 소진한다. 재렌더/새로고침/API 재시도가 여러 번 차감하지 않게 기존 추천 ID 계약을 유지한다.
- 로컬 복원 상태에 비밀번호·휴대폰 인증번호·OAuth 비밀정보를 저장하지 않는다. 기존 진행 상태는 재접속 시 복원하되 콘텐츠 버전·owner·필수 입력을 검증한다.
- 저장 실패 화면에서 성공으로 표시하지 않는다. 동일한 submission ID로 재시도해 중복 기록을 막는다. 오류와 빈 상태에 새 더미 기록을 넣지 않는다.
- 회원 기록 요청은 실제 인증을 검증하는 서버/Firestore 규칙에 연결한다. UI에서 회원 체크만 바꾸는 방식은 금지한다.

## 7. 인증과 동의

- 아이디/비밀번호 직접 가입, 카카오·네이버·Google 소셜을 기존 연결에 맞게 구현한다. 이메일은 정보 필드이며 사용자 로그인 ID로 강제 전환하지 않는다.
- 현재 저장소의 username 인증 브리지/기존 Firebase Auth를 먼저 확인한다. Firebase 기본 이메일 로그인과 username 로그인이 같다고 가정하거나 프런트에서 비밀번호 해시/계정을 자체 저장하지 않는다. 이 UI 업데이트를 이유로 인증 구조를 불필요하게 재작성하지 않는다.
- 회원가입: 비밀번호 확인·휴대폰 인증·정보용 이메일·필수 개인정보 동의와 비의료서비스 확인. 아이디 중복, 비번 조건, 번호 포맷·이미 사용한 번호 정책은 기존 서버 계약을 표시한다. 시안에 없던 정책을 임의로 성공시킬 수 없다.
- 인증하기→코드 입력/만료/재발송→가입 화면 복귀. 실제 검증에 성공해야 인증 완료 표시. 로컬 코드 123456은 운영에 넣지 않는다.
- Google은 실제 provider 연결, 카카오·네이버는 서버에서 토큰 검증하는 기존 OAuth 연결을 재사용한다. 비밀키는 프런트 번들·Git에 넣지 않는다. 제공자별 준비 여부/취소/오류를 실제 상태로 표시한다.
- 새 소셜 사용자에게 필요한 동의/프로필/전화 인증은 기존 가입 정책에 맞춰 적용한다. 동의 안 된 사용자를 완성 회원으로 처리하지 않는다.
- 비회원 첫 진입은 ‘의료서비스 아님’ 동의만. 회원은 두 필수 동의. 거절하면 서비스 본 흐름을 이용할 수 없다. 동의 상세 ‘보기’는 실제 운영 문서를 띄운다.
- 읽은 `lib/service/policy.ts`는 draft-v1 / reviewedForLaunch=false, 운영 보유기간 미정이었다. 실행 시 최신 운영 문서로 확인해 수집 항목·목적·보유기간·운영자 정보·동의 버전을 정확히 반영한다. 로컬 시안의 설명을 실제 개인정보 약관으로 배포하거나 flag만 true로 조작하지 않는다. 정보가 없으면 해당 UI와 준비 상태는 완성하고 꼭 필요한 운영 정보만 최종 보고한다.

## 8. 이번에 메운 빈 화면/상태도 구현

`screen-audit.md`의 16~28번을 모두 연결한다: 비회원 첫 동의, 소셜 첫 동의, 휴대폰 인증, 비회원 하루 제한, 기록 없음, 대체 동작 없음, 네트워크 오류·재시도, 스트레칭/쇼핑 준비, 추천 처리 중, 동의 거절, 회원전용 접근, 선택 자세의 콘텐츠 없음, 기록 저장 실패.

로딩은 실제 비동기 요청 중 자동 표시되고 성공/실패 시 자동 전환해야 한다. 통합본의 “추천 화면 확인”은 검토용이므로 제품에 넣지 않는다. API 오류는 개발 정보 대신 사용자에게 필요한 짧은 메시지/재시도만 표시한다. 빈 화면·미연결 제공자를 숨기려고 가짜 성공을 사용하지 않는다.

## 9. 구현과 검증

기존 프로젝트 구조에 공통 디자인 토큰/컴포넌트를 추가하고 각 실제 화면을 바꾼다. 정적 시안을 iframe에 띄우는 운영 앱을 만들지 않는다. 원본 `screens/`는 리뷰 근거로 보관할 수 있지만 런타임은 기존 프레임워크와 실제 상태를 사용한다.

현재 package.json의 스크립트를 확인하고 lint/typecheck/콘텐츠 체크/build와 관련 기능 테스트를 실행한다. 체크아웃에서 관찰한 스크립트는 content:check, typecheck, test:service, test:emulators, test:browser, test:worker 등이었다. 실제 최신 프로젝트에서 지원되는 필수 검증을 수행한다.

최소 검증:

1. 비회원: 필수 동의→자세→부위→습관→최근→추천→마쳤어요→피드백→완료→재시도 제한. 동의 거절 시 차단. 계정 기록 이관 안 됨.
2. 회원: 실제 로그인/가입·소셜 연결→신규 동의→루틴→각 피드백 분기→자동 기록→부위별 기록→로그아웃/다른 계정에서 기록 안 보임.
3. 평소/최근 배타 옵션·복수 선택·뒤로가기·부위 변경 초기화·재접속 복원. 질문은 정확히 3개, 5부위, 매칭하는 동작 1개.
4. 비슷함·더 불편함에서 유효 대체 없으면 종료. 반복 방문 제외. 불편 답변이 묵살된 채 임의 대체되지 않음.
5. 인증/전송 실패·저장 재시도·중복 클릭·만료 코드·OAuth 취소·로딩·기록 없음·모바일 직접 접근.
6. 320/390/768/1024/1440px에서 가로 넘침과 라벨 겹침 없음. 터치 탭·hover·키보드·font 로딩·원본 이미지 확대·로고 비율 확인.

시안과 실제 앱을 모바일·데스크톱 캡처로 대조하고 눈에 띄는 차이를 수정한다. 필요한 경우 검사 결과를 증거 파일로 남긴다. 통합 검토본의 메모리 테스트를 실 Firebase E2E 테스트로 보고하지 않는다.

## 10. 자산 업로드 및 실제 운영 배포

1. 기존 자산 디렉터리에 최종 로고·캐릭터·인체·동작 11개·폰트를 업로드/커밋한다. MIME·파일경로·대소문자·폰트 라이선스·누락 파일·캐시 버전 확인.
2. 기존 CI/배포 스크립트와 실제 운영 Worker/Pages/도메인 설정을 확인한다. 준비용/preview 환경과 production을 구분한다. 현재 Workers 구성이라면 그것을 그대로 쓴다. Pages 마이그레이션을 새로 시작하지 않는다.
3. 기존 환경변수를 보존한다. 새 정적 디자인 반영 때문에 Blaze·유료 플랜·새 SMS 구매·새 도메인 결제를 켜지 않는다. 필요한 기존 자격/설정만 재사용한다.
4. 검증이 통과하면 작업 내용을 커밋·푸시하고 기존 deploy 스크립트 또는 실제 연결된 CI로 production 배포한다. Git push만 했다고 운영 반영 완료로 선언하지 않는다. 배포 작업 ID/결과와 최신 URL을 확인한다.
5. 운영 URL에서 자산 로딩, 새 UI, 글꼴, 로고, 모든 주요 경로/새로고침, API 연결, 로그인 리다이렉트, 응답 헤더를 점검한다. 에뮬레이터/개발 API를 production에 남기지 않는다. 서비스 워커/브라우저 캐시 때문에 옛 UI가 보이지 않는지도 확인한다.
6. 배포 권한·필수 운영 정책·OAuth/SMS 자격이 정말 없으면 가능한 코드·빌드·프리뷰 검증까지 마치고, 막힌 단계와 정확히 어떤 값/계정 접근이 필요한지만 알려준다. 무관한 새 프로젝트로 우회하거나 기존 데이터/인증을 망가뜨리지 않는다.
